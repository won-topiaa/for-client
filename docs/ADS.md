# 인앱 광고 — 무엇을 왜 고르나

결론부터. **배너(`InlineAd`) 하나만, 1.4.0 출시 후 리텐션을 보고 나서.**
전면형·보상형은 이 앱에 맞지 않는다. 이유는 아래에 적는다.

이 문서는 "나중에 광고 붙일 때 다시 처음부터 조사하지 않기 위한" 기록이다.
API 시그니처는 설치된 `@apps-in-toss/framework@2.10.10` 의 타입 정의에서 직접
확인한 것이고, 콘솔·정산·버전 요구사항은 앱인토스 공식 문서 기준이다.

---

## 왜 배너만인가

| | 판단 | 근거 |
|---|---|---|
| 배너 `InlineAd` | **쓴다** | 화면에 머무는 동안 수익이 쌓인다. 흐름을 끊지 않는다. |
| 전면형 interstitial | **안 쓴다** | 이 앱에 광고를 끼울 자연스러운 구간이 없다. |
| 보상형 rewarded | **안 쓴다** | 줄 보상이 없다. 만들려면 지금 무료인 걸 뺏어야 한다. |

**전면형**을 접은 이유가 중요하다. 전면 광고는 "레벨이 끝났다", "글을 다 읽었다"
같은 **끝나는 지점**이 있어야 성립한다. 이 앱의 동선은 홈 → 지지선 → 종목 →
분석으로 계속 이어지고, 어디에 끼워도 사용자가 하던 일을 자른다. 게다가
정책에 **"서비스 진입 직후 전면 배너 금지"** 가 명시돼 있고, 추천 미니앱 UX
심사 기준에도 걸린다. 몇 만 원 더 벌자고 노출 등급을 깎는 건 계산이 안 맞는다.

**보상형**은 구조적으로 불가능하다. 보상형은 "광고를 보면 X를 준다"인데, 우리
앱에서 X가 될 만한 것(분석 횟수, 관심종목 개수, 패턴 조회)은 **지금 전부 무료**다.
보상형을 넣으려면 먼저 무언가를 잠가야 하고, 그건 기존 사용자에게서 뺏는 것이다.

## 프레임워크가 실제로 주는 것

`node_modules/@apps-in-toss/framework/dist/index.d.ts` 에서 확인한 실물이다.

```ts
declare function InlineAd(props: InlineAdProps): JSX.Element | null;

interface InlineAdProps extends BannerSlotCallbacks {
  adGroupId: string;
  theme?: 'auto' | 'light' | 'dark';
  tone?: 'blackAndWhite' | 'grey';
  variant?: 'expanded' | 'card';
  impressFallbackOnMount?: boolean;
}

interface BannerSlotCallbacks {
  onAdRendered?:       (p: BannerSlotEventPayload) => void;
  onAdViewable?:       (p: BannerSlotEventPayload) => void;
  onAdClicked?:        (p: BannerSlotEventPayload) => void;
  onAdImpression?:     (p: BannerSlotEventPayload) => void;
  onAdFailedToRender?: (p: BannerSlotErrorPayload) => void;
  onNoFill?:           (p: { slotId; adGroupId; adMetadata }) => void;
}
```

`theme: 'auto'` 가 있으므로 **다크 모드는 광고가 알아서 따라간다.** 우리 팔레트를
넘길 필요가 없다.

전면형·보상형도 같은 패키지에 있다(`loadFullScreenAd`, `showFullScreenAd`, 둘 다
`.isSupported()` 동반). 안 쓰기로 했을 뿐 없어서 못 쓰는 게 아니다.

## 반드시 지켜야 할 두 가지 구현 규칙

**1. 높이를 고정하지 않는다.**
`InlineAd` 의 반환 타입이 `JSX.Element | null` 이다. 구버전 토스(배너는 5.241.0
이상 필요)에서는 **`null` 을 돌려준다.** 우리가 `height: 96` 같은 걸 감싸 두면
구버전 사용자 화면에 설명 없는 빈 칸이 남는다. 래퍼에 높이를 주지 말고, 광고가
차지하는 만큼만 자라게 둔다.

**2. 우리 `Card` 로 감싸지 않는다.**
SSP 정책상 광고는 앱 자체 콘텐츠와 구분돼야 한다. 우리 카드(흰 배경·r16·p20)로
감싸면 앱이 만든 콘텐츠처럼 보인다. `variant='card'` 를 쓰든 그냥 두든, 광고가
스스로 자기 테두리를 갖게 한다.

## 붙일 자리

- 화면당 **하나**. 여러 개 붙이면 정책 위반이고 eCPM 도 떨어진다.
- 별표(관심종목 담기)·분석 버튼 같은 **CTA 근처는 피한다.** 오탭은 클릭으로
  집계되지만 그 사용자는 앱을 떠난다.
- 후보는 **지지선 결과 목록 아래**와 **패턴 결과 목록 아래**. 둘 다 사용자가
  스크롤하며 머무는 구간이고, 다음 동작(종목 탭)을 가로막지 않는다.
- **한 화면씩 순서대로.** 이유는 바로 아래.

## 배너는 콘솔 분석 탭에 안 나온다 — 우리가 직접 찍어야 한다

공식 문서의 광고 분석 항목에 **"배너 광고는 아직 지원되지 않아요"** 라고 적혀
있다. 분석 탭 자체가 SDK 2.7.0 이상을 요구하는데, 그걸 충족해도 배너는 집계되지
않는다. 즉 콘솔에서는 **총 수익 합계만** 보이고 화면별로 쪼갤 수 없다.

다행히 위 `BannerSlotCallbacks` 가 그 구멍을 메워 준다. `onAdImpression` 에서
우리 `Analytics` 로 화면 이름을 같이 남기면 화면별 비교가 가능해진다.

그래도 **처음에는 한 화면에만 붙인다.** 자체 로깅을 붙이더라도, 두 곳을 동시에
켜면 총합이 섞여서 "이 자리가 버는 자리인가"를 판단하는 데 한 사이클을 더 쓴다.
한 화면 → 수치 확인 → 두 번째 화면 순서로 간다.

`onNoFill` 과 `onAdFailedToRender` 도 반드시 붙인다. 광고가 안 나올 때
"우리 코드가 틀렸나 / 광고 재고가 없나 / ID 등록이 덜 됐나"를 구분할 유일한
수단이다.

## 코드를 쓰기 전에 끝나 있어야 하는 것

콘솔 작업이 선행이고, 각 단계에 실제로 시간이 걸린다.

1. **사업자 정보** 등록
2. **정산 정보** 등록 → **검토 2~3영업일**
3. **광고 그룹 생성** → 발급된 ID 가 **구글에 등록되기까지 최대 2시간**
4. (선택) 미디에이션 설정

3번의 2시간이 함정이다. 생성 직후 실 ID 를 번들에 넣고 빌드하면 광고가 안 나오는데,
그게 코드 문제인지 등록 대기인지 구분이 안 된다. **개발·테스트는 테스트 ID 로만**
하고, 실 ID 는 스토어 제출 직전에 한 번 교체한다.

테스트 ID (공식 문서)
```
배너      ait-ad-test-banner-id
전면형    ait-ad-test-interstitial-id
보상형    ait-ad-test-rewarded-id
```

## 버전 요구사항 (문서 기준)

| 종류 | 필요한 토스 앱 버전 |
|---|---|
| 배너 `InlineAd` | 5.241.0 이상 |
| 전면형·보상형 (2.0 ver2) | 5.247.0 이상 |
| 전면형·보상형 (AdMob 전용) | 5.227.0 ~ 5.247.0 |

배너가 `null` 을 돌려주는 경우가 여기서 나온다. 위의 "높이 고정 금지"가 그래서 있다.

## 돈 이야기

```
예상 수익 = 노출 수 × eCPM ÷ 1,000
```

| 일 노출 | eCPM 1,000원 | eCPM 2,000원 |
|---|---|---|
| 500 | 월 15,000원 | 월 30,000원 |
| 2,000 | 월 60,000원 | 월 120,000원 |
| 10,000 | 월 300,000원 | 월 600,000원 |

배너 eCPM 은 전면형보다 한참 낮다. 식에서 우리가 움직일 수 있는 변수는 사실상
**노출 수 하나**고, 노출 수는 곧 **매일 들어오는 사람 수**다. 아침 브리핑과
관심종목 알림이 하는 일이 정확히 그것이다. 반대로 재방문이 안 붙은 상태에서
배너부터 달면, 버는 건 거의 없으면서 추천 미니앱 UX 심사 부담만 하나 는다.

**정산 타임라인**: 성과 데이터는 매일 10시 갱신. 정산액은 **다음 달 1일 확정**,
**그달 말일 입금**. 10월에 켜면 첫 입금은 11월 말이다. 앞의 정산 정보 검토
2~3영업일까지 치면 지금 시작해도 두 달 가까이 걸린다. 급하게 켤 이유가 없다는
뜻이기도 하다.

심사에 들어가면 UX 5원칙을 한 번 더 통과해야 한다. 순서를 바꿔서 얻는 게 없다.
